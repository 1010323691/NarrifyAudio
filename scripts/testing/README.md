# 全任务类型混合压测

`mixed_worker_load.py` 从任务注册表核对覆盖范围，每个用户打乱全部 22 种任务的顺序，通过真实 HTTP 登录、CSRF、任务提交、Redis 和独立 Worker 执行。

仅替换模型边界：LLM 使用本地 OpenAI HTTP 服务；TTS 使用真实子进程，输出符合协议的有效音频。业务引擎、任务领取、租约、额度结算、文件事务发布以及真实 FFmpeg 混音保持原实现。测试替身位于 `backend/tests/load_fixtures/`，生产启动不引用它们。

需要项目 Python 环境、可创建临时数据库的测试 PostgreSQL、`redis-server` 和 FFmpeg。示例：

```bash
.venv/bin/python scripts/testing/mixed_worker_load.py \
  --postgres-admin-url 'postgresql://test_user:test_password@127.0.0.1:5432/postgres' \
  --users 20 --workers 4 --model-workers 4 --model-delay 0.2
```

脚本创建独立数据库、Redis 进程、HTTP 服务、音乐库及合成资料，端口自动选择；结束后关闭进程并删除临时数据库。报告、日志及生成文件保留在 `work/mixed-*/`，不要提交生成数据。可用 `--output-dir` 指定输出父目录、`--redis-server` 指定可执行文件、`--deadline` 设置单轮最长等待秒数。测试账号拥有管理员角色，用于覆盖管理员专用的音乐标签任务。

验证包括：所有类型成功、单次领取、无 Worker 提前退出、结果文件用户/项目及 SHA256 正确、LLM 调用次数、TTS 行级结果、角色配置和共享音乐标签并发写入无丢失、额度流水与账户一致且无残留预留、过期缓存删除而新缓存保留。

合并、打包、重置和 BGM 的前置资料独立预置，以免随机顺序产生业务依赖失败。资源扫描、打包和清理使用适当的独立项目，避免扫描改变冻结快照或繁忙项目保护影响本轮成功预期。该场景验证混合调度及业务编排；不验证真实模型推理性能、输出质量或 GPU 模型切换。解析复查阶段关闭；可分别用 `--llm-delay`、`--tts-min-delay`、`--tts-max-delay` 设置延迟。TTS 推理时长按用户和模式确定性分布，包含区间端点；CPU 合并子进程使用 `--merge-delay`（默认 0.2 秒）。短冒烟测试仍可用 `--model-delay` 提供默认值。比较不同 Worker 数时，保持用户数、延迟和机器负载一致。

## 接近业务耗时的模拟

```bash
.venv/bin/python scripts/testing/mixed_worker_load.py \
  --postgres-admin-url 'postgresql://test_user:test_password@127.0.0.1:5432/postgres' \
  --users 20 --workers 4 --model-workers 4 \
  --llm-delay 10 --tts-min-delay 10 --tts-max-delay 60 --deadline 1800
```

这里的 TTS 延迟针对每次合成/声音设计子进程返回，不按文本中的每行额外累加；合并不加载 TTS 模型。报告记录各次模拟等待的计划时长和实际时长，以及任务租约续期观察数。任务排空期间轮流读取用户任务列表，检查模型等待期间 API 是否仍能正常响应。默认生产租约保持不变。

当前脚本默认运行 4 个机械 Worker + 4 个模型 Worker；`--workers` 表示机械进程数，`--model-workers` 表示额外的模型专用进程数，两组都必须至少为 1。每次领取记录都校验所属分工。上面的历史对照表对应引入强制独立分工之前的混合 Worker 行为。

### 强制分工与长任务保护

生产入口 `python -m backend.worker_pool` 监督 4 个机械进程和 4 个模型进程，退出的槽位按原分工重启。机械组覆盖 15 种非模型任务，模型组覆盖 7 种 LLM/TTS 任务；两组不能互相领取，合并音频属于机械组。单独启动 `backend.worker` 时必须选择 `--task-lane mechanical` 或 `--task-lane model`，默认机械组，不再支持混合模式。

同一项目的冲突写入在领取前检查，繁忙任务保持 pending，不创建执行尝试、不占执行槽；不同项目或不同目标的兼容音频合并仍可并行。真实耗时的早期诊断曾暴露任务领取后等待项目文件锁超过 30 秒而重试，新增领取保护避免此类槽位阻塞。项目文件锁仍作为执行阶段的防线。

本次完整后端检查：1,446 项通过、13 项跳过，6 项既有失败与上文一致；分层检查通过。另有 3 项真实 PostgreSQL 公平领取与项目并发保护检查通过，监督进程的实际 8 子进程重启、分工及退出清理检查通过。

### 独立 4+4 Worker 真实等待压测结果

20 用户、全部 22 种任务共 440 个，LLM 每次实际等待 10 秒，TTS 推理/声音设计实际等待 10～60 秒：440 个全部成功，总耗时 686.013 秒，整体吞吐 0.641 个/秒。此吞吐包含模型长等待，不能与上方 0.2 秒历史模拟直接比较。

机械组 300 个任务在提交开始后约 91.3 秒全部完成，模型组 140 个任务继续运行至约 685.5 秒；两组每条领取分工校验通过。机械任务执行耗时 P95 为 2.646 秒、排队 P95 为 41.901 秒；模型任务执行 P95 为 55.153 秒、排队 P95 为 593.465 秒。排队时间包括并发提交积压和必要的同项目写入顺序，不代表机械 Worker 被模型占用。

任务失败、重试、Worker 意外退出和业务校验错误均为 0；380 次产物用户/项目及 SHA256 校验通过，额度预留与模型许可残留均为 0。观察到 122 个执行尝试续租；排空期间 308 次 API 查询均成功，响应 P95 为 0.106 秒。数据库连接采样峰值 73。TTS 实际等待范围为 10.000～60.001 秒，LLM 四种调用各 20 次。本轮使用模型替身且关闭动态 GPU 服务管理，真实 GPU 切换及推理并发容量仍需单独验证。
