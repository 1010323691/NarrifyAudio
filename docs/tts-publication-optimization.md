# TTS 结果发布性能优化方案

## 现场证据

2026-10-08，testuser001 的音频合成任务，项目名称不写入运行参数或代码。以下时间使用服务器时区 UTC+9。

- 下午批次于 13:50 启动，41,781 个待合成分段的音频文件在 13:51:40—15:51:07 持续生成，文件生成时间的最长间隔约 35 秒。
- 18:01 左右核对时，19,933 段进入正式目录，21,848 段仍在暂存目录；逐一按章节、分段索引匹配，缺失文件和小于 100 字节的文件均为零。这是文件完整性核对，不代表逐段试听验收。
- 合成子进程已退出，退出码为 0，GPU 空闲。后台继续消费积压结果；旧日志的入库时间晚于真实生成时间。
- 正式目录接收量约为：14 点小时 7,155 段、15 点小时 3,778 段、16 点小时 2,892 段、17 点小时 2,412 段，发布速度随任务规模增长而下降。
- 后续采样的 v1 恢复记录有 37,721 条，文件 12,559,005 字节：音频记录 20,727 条、manifest 记录 16,600 条、其他记录 394 条。Worker 累计写盘已超过 213 GiB；这是累计 I/O，不是日志占用空间。

## 性能测量和根因

使用上述恢复记录的快照，在临时目录复现旧代码的记录构造、JSON 写入、fsync、重命名流程，执行三次取均值；不改动任务、音频或现有恢复记录。运行中的 Worker 会影响绝对耗时，因此结果用于识别瓶颈，不作为生产吞吐承诺。

| 单次旧恢复记录重写阶段 | 平均耗时 |
| --- | ---: |
| 遍历全部记录、计算相对路径、构造字典 | 696.45 ms |
| JSON 序列化、写入、flush | 66.52 ms |
| fsync | 2.21 ms |
| 恢复记录重命名 | 0.88 ms |
| 总计 | 766.07 ms |

对照：新代码追加注册 128 条 checkpoint 记录耗时 3.53 ms、写入 16,830 字节；创建并重命名 128 个 1 KiB 临时文件耗时 1.98 ms。该对照未包含完整发布链路的数据库、额度、manifest 和事件成本。

最主要的瓶颈是旧 PublicationJournal.add() 每次复制历史条目，然后 _write() 为所有历史记录重新生成路径和 JSON。单次成本随记录数线性增长，全任务累计接近 O(N²)。样本中路径和记录构造占单次重写时间约 91%，所以仅减少 fsync 或压缩普通日志不能解决问题。

结果回调还串行执行音频发布、额度消费、清单刷新和进度统计。前面的恢复记录操作慢，会阻塞后续结果处理。音频已经在暂存目录生成，进度和正式文件却滞后；日志中“生成中”也可能是积压消息。

次要成本：

1. manifest 的重复发布也进入同一恢复记录，每次构造完整章节清单，并对历史恢复记录再次执行全量重写。
2. 每段额度消费查询幂等键、锁定额度账户和预留记录、写入流水并单独提交。
3. 章节统计反复扫描全部章节和分段。变更章节的 segments 和 progress 事件分别走数据库操作。
4. 结果接收与上述工作绑定在一个串行回调中，缺少明确的积压量和阶段耗时指标。

次要成本由代码确认，尚未通过完整生产链路分段计时确定其占比。

## 第一阶段：先消除全量重写

以下改动已经在工作区落地并完成测试，但当前旧 Worker 尚未加载。

- 恢复记录改为 v2 NDJSON，只追加新增注册记录和必要指纹；相对路径在注册时生成，避免重复遍历历史条目。兼容 v1 恢复记录。
- 音频发布累计到 128 段或 250 ms 后批量注册，一批一次持久化；先持久化恢复意图，再移动文件。
- 清单和对外进度发布前，先冲刷音频队列，确保清单不会指向尚未发布的文件。
- manifest 仅在 dirty 时写入；成功后清除 dirty，结束和取消时也只写需要更新的章节。刷新节流从刷新完成时开始计时，避免慢刷新导致连续触发。
- 子进程退出后明确显示“正在保存合成结果”；正常日志只保留批次摘要、阶段切换和有限错误样例。

此前模拟约 42,000 条注册记录的测量结果：恢复记录约 5.37 MB、注册耗时约 1.02 秒、330 次 fsync。它不包括音频移动、额度、任务事件和章节合并，不能当作整批任务耗时。

## 第二阶段：减少数据库和统计成本

第一阶段上线并采集指标后执行，避免在没有数据的情况下增加并发复杂度。

### 批量额度记账

- 按发布批次汇集分段消费，每批一个事务；保留每段幂等键和流水，账户及预留额度按实际新增消费总量更新。
- 多章节涉及多个预留时使用固定锁定顺序，避免死锁。重复提交不重复收费，已取消章节不消费后续分段。
- 发布成功而额度事务失败时，重试同一批次，不重新生成音频；在幂等额度确认前不宣告章节完成。
- 保持现有预留和释放语义，不使用“成功计数乘平均字数”近似收费。

### 增量统计与合并事件事务

- 缓存各章节总段数、总字数；首次确认某分段成功时，只更新对应章节计数，避免全量扫描。
- 仅处理计数发生变化的章节；使用单调时钟节流，建议 500 ms—1 s 合并一次对外更新。
- 同一章节的任务进度、segments 事件和 progress 事件放在同一事务中更新，保留现有前端协议。
- 完成、取消、失败时强制提交最终状态；租约续期独立于发布和进度节流。

## 第三阶段：明确结果接收与发布的边界

- 子进程输出带真实生成时间、批次标识和分段标识。分别记录生成时间、接收时间、发布时间，避免消费时间被误读为生成时间。
- 接收端只解析、校验并登记待发布结果，发布端批量处理恢复记录、移动、额度和清单。磁盘上的分段文件及持久化结果索引作为恢复依据，不能只依赖内存队列或 stdout。
- 队列有容量上限，满时采用背压；同一任务的恢复记录保持单写者。章节完成依赖发布、额度确认和清单落盘，不依赖子进程退出。
- 如果要求较早得到完整章节，再单独评估有限章节窗口组批；它可能降低 GPU 吞吐，不作为本次发布瓶颈的首要修复。

## 可观测性与验收

每 30 秒输出一条聚合摘要：generated、published、pending_publish、chapters_complete、publish_rate、journal_bytes_written，以及恢复记录、文件移动、额度事务、清单和事件提交各自的累计耗时。错误即时记录；正常流程不输出逐段日志。

验收目标（上线实测确认）：

- 42,000 段、620 章规模下，恢复记录写入量随新增记录近似线性增长；10k、20k、40k 时发布吞吐不再随历史记录规模明显下降。
- 第一阶段恢复记录本身写入量目标低于 20 MB；完整发布吞吐目标不低于 100 段/秒，生成结束到发布完成目标低于 10 分钟。这些是目标，不是已验证结果。
- 稳态发布能力至少覆盖生成速度；若无法覆盖，摘要清楚显示积压和瓶颈阶段。
- 每段都有正式文件或可恢复暂存文件；未发布、未记账、未落清单的章节不能标为完成。
- 覆盖注册前、注册后移动前、移动部分完成、额度提交前后和清单提交前后的进程终止恢复；验证取消、同项目并发更新和重试幂等性。
- 保持 v1/v2 恢复兼容，运行完整后端测试以及前端类型检查、构建和分层门禁。

## 上线顺序

先启用第一阶段，采集发布阶段指标，再决定第二阶段和第三阶段的投入。已有运行任务不通过替换正在写入的恢复记录热升级。当前批次若要提前切换新 Worker，需先设计并验证暂存结果和旧恢复记录的接管流程，不能直接杀进程后假设结果会自动全部发布。


## 实施与验证记录（2026-10-08）

第二阶段已落地：`consume_tts_inputs` 每批一次额度事务，保留逐段流水与幂等键；多预留锁及释放锁按操作名称排序。章节计数按分段状态变化增减，统计只向变化章节提交；segments 和 progress 在同一租约检查和事务内更新，提交失败不缓存成功快照。

正常运行每 30 秒追加一条发布统计，显示实际文件数量、已发布数量、暂存积压、速率、恢复记录写入量和各阶段累计时间。清单总耗时包含清单本身的登记和移动成本，与底层计时存在重叠，不能将所有时间直接相加。现阶段仍沿用既有子进程输出队列；独立持久化结果索引及发布消费者属于第三阶段，根据上线指标另行评估。

验证：

- 完整后端：`pytest backend/tests -n 4 --dist loadscope`，1443 passed、17 skipped。
- `npm run build:all` 通过，包含前端类型检查、构建、Python 编译和分层检查。
- 使用独立的临时 PostgreSQL 集群，两个并发用例通过：8 个并发请求重复提交同一额度批次；释放额度与批量消费并发。集群与数据已销毁，未连接生产数据库。
- 在工作空间所在 ext4/NVMe 的独立临时目录模拟 42,000 个 1 KiB 文件、620 个章节，执行 128 段批量登记和移动、逐段额度流水的批量提交、每章一次最终清单和最终进度事件。总计 7.29 秒，约 5765 段/秒；恢复记录 4,672,842 字节、949 次追加 fsync。各部分耗时：模拟文件创建 0.37 秒、登记与移动 1.69 秒、额度事务 3.01 秒、最终清单与事件 2.21 秒。核对额度消费和流水均为 42,000，暂存目录为空。
- 上述压测使用 SQLite，没有音频编码、真实子进程回调、逐行控制检查、持续清单刷新或生产 PostgreSQL/队列开销，不能作为完整生产任务的吞吐承诺。
